# Shims and receipts

Agents run tests the way people do: `cargo test 2>&1 | tail -20`,
`cd pkg && pytest -q | grep FAILED`, loops, `timeout`, subshells. In 50 real
Claude Code sessions (2,887 Bash calls), 56% of commands were piped through
`tail` or `head`, and 76% of test/build/lint runs were cut by `tail`, `head`,
or `grep`. Only 4% of test commands were simple enough to rewrite without
parsing shell, so `prog` does not rewrite command strings at all.

Instead it captures at the point where the shell has already done the parsing.

## PATH shims

```sh
prog shim install                 # ~/.local/share/prog/shims by default
eval "$(prog shim env --project "$PWD" --shell)"
```

`prog shim install` writes a two-line `sh` script per tool (`cargo`, `pytest`,
`py.test`, `go`, `npm`, `pnpm`, `yarn`, `bun`, `deno`, `jest`, `vitest`,
`playwright`, `tsc`, `ruff`, `biome`, `uv`; `--tool` picks others):

```sh
#!/bin/sh
# prog-shim: generated by `prog shim install`; remove with `prog shim uninstall`.
exec /path/to/prog shim exec --shim-dir /path/to/shims -- cargo "$@"
```

When the shim runs, the shell has already split the command line, so it
receives the exact argv however the command was written. `prog shim exec`
then:

1. finds the real tool later on `PATH`, skipping the shim directory;
2. `exec`s it directly unless the [route classifier](../crates/prog-core/src/route.rs)
   marks the argv as progressive (test, build, lint), or the call is nested
   inside another shimmed tool;
3. otherwise runs it with the same argv[0], stdin, and environment (plus
   `PROG_SHIM_ACTIVE=1`), and relays every byte to the destination it would
   have reached. When stdout and stderr share one target (`2>&1`), the child
   gets a single pipe, so interleaving is unchanged;
4. imposes no deadline (the harness owns timeouts), ignores interactive
   interrupts the child already receives through the process group, forwards
   `SIGTERM`/`SIGHUP`, and exits with the child's code or dies by its signal;
5. records the complete output as an ordinary `run` observation, with the same
   redaction, coding provider, findings, and comparison as `prog run`.

If the reader goes away early (`| head`), the child sees the same broken pipe
it would have seen, and the capture is marked truncated so it can never prove
absence. Recording problems are silent: a broken or missing store never
changes the command's output or status.

`prog shim install` never overwrites a file it did not generate, and
`prog shim uninstall` removes only generated shims.

### Evidence

`crates/prog-cli/tests/shim.rs` runs 14 agent-shaped pipelines with and without
the shim directory on `PATH` and requires byte-identical output and identical
`PIPESTATUS`, including `set -o pipefail`, `tee`, `nice`, subshells,
`> /dev/null 2>&1`, and a 200,000-line `| head -3` that ends in `SIGPIPE`. It
also checks signal forwarding, foreign-file safety, and that a broken store does
not change anything.

Measured overhead on macOS (release build, median of 30): a call that is not
captured (`cargo --version`) adds 7.9 ms. A captured run adds about 180 ms,
which is the cost of recording the observation (store commits). That is small
next to a test suite, but it is real; recording after the shim returns is a
possible follow-up.

### Limits

- Tools started by absolute path, or found earlier on `PATH` than the shim
  directory (for example `.venv/bin/pytest` under `uv run`, or
  `node_modules/.bin/vitest` under `npx`), bypass their own shim. `uv` and
  `npx` themselves are captured when their argv is progressive (`uv run ...`);
  `python -m pytest` is not shimmed.
- `rustc` and `git` are not shimmed by default: Cargo invokes `rustc` per
  crate, and agents call `git` constantly.
- When stdout and stderr share a target, the capture cannot separate them and
  stores the merged stream as stdout.

## Receipts

```sh
prog receipt                 # latest observation
prog receipt <observation>   # a specific one
prog receipt --pending       # shim captures not yet reported, consumed once
```

A receipt is built only from the persisted, redacted payload and, when the
same invocation ran before, the same delta `prog delta` reports. The store
links each capture to the previous capture of the same canonical invocation
(`lineage.supersedes_id`), so no flags are needed:

```text
prog: `cargo test --no-fail-fast` · exit 101 · 1 passed, 1 failed: tests::adds · full output kept (33 lines)
first failure: tests::adds panicked at src/lib.rs:6:25
evidence: prog evidence pc1_… --path /failure_sections/0
```

```text
prog: `cargo test --no-fail-fast` · exit 0 · 2 passed, 0 failed · full output kept (16 lines)
vs previous run: fixed: tests::adds
evidence: prog evidence pc1_… --path /stdout
```

`verdict` is `failing`, `fixed`, `not_proven`, or `clean`. `fixed` requires the
delta's absence proof, including the test-population rule in
[delta.md](delta.md): a clean rerun after deleting, skipping, or ignoring the
failing test is `not_proven`. On a real Rust project the receipts above were
208–287 bytes; the envelopes for the same runs were 8.6–13 KB.

## Claude Code plugin

[`plugins/prog-claude`](../plugins/prog-claude) wires this together with one
tested entry point, `prog harness hook claude-code`, which reads the hook
input on stdin:

| Event | What happens |
|---|---|
| `SessionStart` | Installs shims, appends `PATH` and a per-project `PROG_DIR` to `CLAUDE_ENV_FILE`, records the session start. The store lives under `~/.local/state/prog/projects/`, outside the project, so captures never count as workspace changes. |
| `PostToolUse` / `PostToolUseFailure` (Bash) | Adds pending receipts as `additionalContext`. The tool output itself is never changed. |
| `Stop` (opt-in) | When the `stop_gate` plugin setting is on, blocks once if the head of any test-run chain from this session is failing or not proven, or if files changed after the last passing run. `stop_hook_active` lets the next stop through, so the agent can always explain and finish. |

Every unexpected condition produces no output and exit status 0. The plugin is
covered end to end by `crates/prog-cli/tests/claude_code_hook.rs`, which feeds
hook-input JSON exactly as Claude Code does and runs commands through `bash`
with the session exports applied.
